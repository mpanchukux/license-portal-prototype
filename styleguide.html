Tokens

The variables on :root. Swatches and sizes are read from the live stylesheet at load, so they cannot drift from the values the product uses.

Colour

Monochrome by constraint: state is carried by weight, border and fill — never by hue.

Type scale

Nine levels across two tiers plus the key, a 14px floor, and weight that grows with size (700 only on display and h1). The compact tier is what ≤600px substitutes for h1, h2 and body — the phone is not the desktop scale shrunk, it is its own three sizes.

⚠ display currently has no user. It was written for numbers that carry a page, briefly styled the landing page’s Welcome, and lost that when the landing head was reduced to one heading — the H1 there takes h1 like every other page. The level is kept and documented rather than deleted, because a scale with a hole in it is harder to read than one with an unused top step; but nothing in the product renders it today.

LevelTokenSize / line / tracking / weightSpecimen

Exceptions, all of them. Every other hardcoded size in the stylesheet is one of these, and nothing else is allowed to join the list without moving into the table above.
· Glyph sizing — 22, 20, 19, 18, 16, 15 and 13px set the box of a text-glyph button (⋮, ×, +, ←), not the size of any text. A glyph is an icon that happens to be a character; it takes the size its target needs, and 13px on .kn-x is the only sub-floor number anywhere because nothing there is read.
· Levels written as literals — 106 rules say font-size:14px and 11 say 16px where they mean small/label and body. The rendered scale is correct — only the authoring is loose. Not a second scale, and not a reason to read a number off the stylesheet instead of off this table.
· 17px tr.lic-row .lp-head — the licence name on a phone card, one step above body-sm so the card has a clear headline. The only 17px in the prototype.
· 14.5px .am-celltop — a half-pixel nudge on the add-ons matrix so a long cell fits its column. Below the floor by half a pixel; kept because rounding it up reflows the table.
· Two mono stacks — .mono uses the raw system stack, while --font-mono (Ubuntu Mono) is used only by .nl-keybox code and this page’s own chrome. The key therefore renders in two different faces depending on where you meet it.

Error state .field.err > .fielderr

Monochrome, so the fault is not carried by hue: the border goes to ink and thickens, and the reason appears under the field in the slot .help would have used — .help is hidden while an error shows, because two lines under one field, one of them now wrong, is worse than either alone. The message says what is wrong, not that something is. “Use MM / YY” can be acted on; “invalid” cannot.

⚠️ No glyph on the message. It carried a drawn (!) circle and that mark was removed: in a monochrome system it repeats what the message already says, while costing a hanging indent that pushed a two-line error out of line with everything else under the field. The fault is signalled twice already — the border thickens to ink, and this line is ink and bold where .help is faint and regular.

The rule that goes with it: a primary action is never left disabled with nothing said. Either it is enabled and answers on submit — painting every failure at once and moving focus to the first — or it is disabled with the reason visible beside it. The purchase wizard’s billing step and the update-card modal both take the first form, and a .formerr summary sits with the button naming how many fields are waiting. Fields answer on blur, and typing again withdraws the answer.

Info icon .infoic.tip.wide

The explanation a row’s name needs, one hover away — for a description worth reading once, to decide, on a row whose name and number get read every time. Built from infoIcon(about, text) in components.js; the text rides in data-tip, so there is no second copy of it in the DOM.

AI credits hover me

Rules. It is a <button>, so Tab reaches it and Enter opens it; aria-label names what is explained (“About AI credits”), never the explanation itself. Desktop opens on hover and :focus-visible. Below 600px there is no hover, so a tap toggles .show — one delegated handler in shared.js, which stands down entirely on a pointer device so a click never pins a bubble hover is about to show anyway. There the bubble also anchors to the heading rather than the glyph, which is what keeps a 300px bubble on a 375px screen.

When not to use it. If the description is what the reader is choosing between — an add-on they may or may not want — it stays as body text. Hiding it behind an icon would hide the thing being decided.

Alert icon .alertic.tip.wide

Two icons, two meanings, and the difference is the whole reason there are two. The info icon above explains something neutral — what a production instance is, what an AI credit buys — and a reader who never opens it has lost nothing. This one says something is wrong, and in a list row it is the only mark that does. If they looked alike, a row would answer “is anything the matter here?” with a glyph that means either.

Active hover me
AI credits the neutral one, for contrast

How they differ, and it is not only the shape. Info is a hairline ring in --faint; alert is a filled triangle in --ink, with the exclamation knocked out of the fill. Fill is the strongest emphasis this system has, and it is what the attention chips already use. Same size, same tooltip mechanics — hover on a pointer device, tap below 600px, because touch has no hover and an explanation only reachable by hover is not reachable.

⚠ Not in an error colour, and that is a departure from what was asked. This prototype is monochrome by hard rule — state is carried by weight, fill and shape, never by hue — and a single red glyph would be the only colour in the product. Adding an --error token is a one-line change if that rule is being revisited; it is recorded here rather than made quietly.

Keep the row's own label short. In the table the icon carries a few words. The full sentence — what is actually lost — lives on the licence page, where there is room to say it once, properly.

The Home banner slot #homeBanner · .gbanner.homebanner

One slot, one banner, a stated priority order — and two shapes inside it. One licence needs attention: two short lines, the fact (licence in bold) and what to do. Several: the banner becomes a short list — up to three lines, each naming a licence, its problem and its action, in the same priority order — then and N more linking to the filtered list (licenses.html?attention=1).

⚠ This supersedes the earlier rule that only the highest-priority condition rendered and the rest became a count. The count told the reader that something else was wrong but not what, so the only way to find out was to go looking. What has not changed is why that rule existed: three stacked banners would push the licence list off the screen. Three lines do not — measured at 390px, three lines plus the overflow link are 270px, a third of the viewport, entirely above the fold.

Home says what is wrong and what fixes it; the explanation lives one click in. The migration sentence (“this usually happens after moving a deployment…”) belongs to the licence’s own banner and the line above the Instances list, not here — on Home it was the longest thing in the band and the least useful to someone who already knows what they did.

The ✕ on a list dismisses the lines it is showing, each under its own key — so they still return independently, each at its own next threshold. One ✕ per line would put three close buttons in a band four lines tall. And the ✕ is absent whenever any line is blocking, not only when the first one is.

Dismissal is per licence AND per state. The key is <licence id>:<state>, so closing one notice can never silence a different licence, a different problem, or a later stage of the same one: B11:updates_30 and B11:updates_14 are different keys, so the 14-day notice arrives as if nothing had been dismissed. That is why the stage is in the key rather than in a value beside it. The two “returns after N days” rules store the day dismissed, not a boolean.

⚠ Blocking states cannot be dismissed, and that is deliberate. Blocked, payment failed and no-payment-method are all conditions where something has already stopped working or is about to, and where the portal is the only place the person finds out. A dismissible blocker is a blocker that gets closed once and never seen again, and the next contact is a support ticket asking why the deployment stopped. Time-based warnings are the opposite: they come back on their own, so dismissing one costs nothing.

Home notifies; the licence records. The same conditions appear on the licence page in #subAlert and are never dismissible there — Home is a notification surface, the licence is the record of state.

A cancelled licence that is still active until its end date gets no banner. Nothing needs doing, and the state is already on the licence and in the list.

⚠️ “Waiting for its first instance” is no longer one of these. It was condition 8. A licence that has not been activated yet is a fact about that licence, not something Home has to interrupt with: nothing is broken, nothing is about to stop, and the person who just bought it is already looking at it. The state itself is untouched — the licence's own banner still explains it and links to the installation guide.

The same conditions mark the rows in the list, through the same function (attentionOf) — the banner links into a filtered list, and if the list decided “needs attention” its own way the two could disagree about which rows belong in it. The marker is the alert icon plus a few words in the status cell; the full sentence is on the licence. ⚠️ The two account-level conditions (no payment method, card expiring) have no licence to mark — they would put the same triangle on every row — so they appear in the banner only.

The Instances view #instancesList

A view, not a nav destination. A typical customer runs two to five instances; a top-level page for five rows costs more attention than it returns. The Licenses page carries a .lic-viewseg toggle — same page, same toolbar, two ways of slicing the same data. Columns: instance · licence · last check-in · version · status. Nothing about plans or money lives here — that is what the licence row is for.

The shared toolbar has to stand down. The type chips and the canceled switch filter licences, and an instance has neither a type nor a cancellation, so they are hidden in this view rather than left disabled. Search stays: both views are rows.

Detach lives on the instance row and nowhere else. The blocked banner does not implement a second one — it routes here, the same way the payment-failed banner routes to the card modal. Discovery is handled by copy, in two places: the blocked banner (“This usually happens after moving a deployment to a new server…”) and a quiet persistent line above this list (.inst-hint). Two sentences, no second button.

The confirmation is destructive treatment, because this turns off live infrastructure. It names the instance — there is no “are you sure?” about an unnamed thing when the whole point is picking the right one of several — shows its full ID and last check-in, and says what happens and when: the server keeps running until its next check-in, within the hour, and then stops. The seat is freed immediately, so the replacement can be activated with the same key straight away.

Where a message goes — two places, one rule each

⚠️ A single action used to produce two messages at once — a bar inside the licence panel and an inline note under the key. Split by kind, each kind has exactly one place, and nothing invents a fourth.

1 · Result of an action → snackbar. Something the person just did, which is finished and will not become truer by staying on screen: plan changed, capacity purchased, add-on removed, coupon applied, label saved, payment method updated, subscription cancelled, updates renewed, invoice downloaded. It lives outside the licence panel — bottom of the viewport on desktop, top below 600px — and leaves on its own.

2 · Persistent state → the slot below the panel header (#subAlert). Facts that stay true until something changes: payment failed, over the instance limit, cancelled and active until a date, software updates expiring. One at a time. If two are true, show the more serious one and name the other in the same banner rather than stacking — two banners is two problems competing for one glance and pushing the licence off screen. Nothing transient goes here.

⚠️ There used to be a third place: scheduled changes, in the Plan block (#schedLine) — a line stating that a lowering change would take effect on a future date, carrying the action that cancelled it. It is gone, and so is the thing it described. Downgrades recalculate immediately, so no change is ever pending: there is nothing to announce between deciding and it happening, and nothing to cancel. What the reader needs is said before they commit, on the Review step (.nl-effect) — what is being given up, the new price, and that it starts immediately — and afterwards by the snackbar, like every other completed action.

The one banner that sits above the header is #licNewBanner — License created. It is above the title precisely so a newly created licence with a problem can show it and the state banner at once without colliding. It appears once per licence, ever: the seen mark is written when it is shown, not when it is dismissed, so closing and reopening the panel — or reloading — does not bring it back.

Exception, and it is deliberate. License key copied and Instance ID copied answer in the button's own tooltip, not the snackbar: a copy is a micro-action on a small control, and an answer at the edge of the screen makes the reader look away from the thing they just pressed. The tooltip is already there and already says what the button does; for 1.2s it says what it did.

Bottom sheet .dprofmenu · #headKebabPop · .permenu

Below 600px a menu with more than two items stops being an anchored dropdown and becomes a sheet at the bottom edge. Three of them exist: the profile menu, the licence ⋮ overflow, and Activity’s period filter. One declaration covers all three — they had drifted apart and were each missing the same things.

The three requirements. A grab handle (36×4, centred) so the thing reads as a sheet rather than a panel that appeared; 22px under the last item, because a list ending flush against the screen edge gives no way to tell whether it continues; and scrolling at max-height:72vh, or a sheet taller than the viewport silently loses its tail. ⚠️ All three were absent, and a participant closed these by guessing at the dimmed area. The handle is a ::before, so a sheet needs no extra markup to get one.

Snackbar .snack

A transient message that reports something happened, then leaves on its own (4.2s) — with a dismiss for the impatient. Two anchors, one per breakpoint. On the desktop it sits at the bottom of the viewport, in the margin below the content. Below 600px it anchors to the TOP, 12px under the app bar. ⚠️ That is not a preference: at the bottom of a phone it has to clear the bottom navigation and the prototype’s gear, and every offset that clears both lands it in the middle of a short viewport, over the content it is confirming — measured at 393×748, all three confirmations came up mid-page. The top has one fixed thing to clear and nothing pinned below it. role="status", not alert — an alert interrupts, and a confirmation of something you just did has no business taking the cursor.

Confirmations leave; problems stay. The snackbar carries completed actions — Invitations sent to 3 people, Invite link copied. It never carries a field error: Already has access, an invalid address, an empty required field all stay inline beside the input, because the person reads them while fixing the thing they describe, and a message that removes itself on a timer is the worst place for an instruction someone has to act on.

Snackbar or saved note? .snack vs .savednote

They coexist, and they are not two ways of doing one thing. The split is what the message is, not how loud it should be.

 Saved noteSnackbar
Saysa persistent fact about a form — these values are stored, as of thena transient event on a list — this just happened
Livesbeside the button that caused it, in the layoutoutside the layout, at the bottom of the viewport
Leaveswhen the next edit contradicts iton a timer
Used onAccount, Billing, Security — pages with a page-level SaveUsers — pages with a list and no page-level Save

They never appear on the same surface, which is why the pair does not compete: a page either has a Save whose result is a stored state, or it has a list whose result is a changed row. A page-level Save reporting into a snackbar would put a fact on a timer; a list action reporting into an inline note would leave a receipt sitting next to a control the reader has finished with.
