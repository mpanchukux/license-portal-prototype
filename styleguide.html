Tokens

The variables on :root. Swatches and sizes are read from the live stylesheet at load, so they cannot drift from the values the product uses.

Colour

Monochrome by constraint: state is carried by weight, border and fill — never by hue.

Type scale

Nine levels across two tiers plus the key, a 14px floor, and weight that grows with size (700 only on display and h1). The compact tier is what ≤600px substitutes for h1, h2 and body — the phone is not the desktop scale shrunk, it is its own three sizes.

⚠ display currently has no user. It was written for numbers that carry a page, briefly styled the landing page’s Welcome, and lost that when the landing head was reduced to one heading — the H1 there takes h1 like every other page. The level is kept and documented rather than deleted, because a scale with a hole in it is harder to read than one with an unused top step; but nothing in the product renders it today.

LevelTokenSize / line / tracking / weightSpecimen

Exceptions, all of them. Every other hardcoded size in the stylesheet is one of these, and nothing else is allowed to join the list without moving into the table above.
· Glyph sizing — 22, 20, 19, 18, 16, 15 and 13px set the box of a text-glyph button (⋮, ×, +, ←), not the size of any text. A glyph is an icon that happens to be a character; it takes the size its target needs, and 13px on .kn-x is the only sub-floor number anywhere because nothing there is read.
· Levels written as literals — 106 rules say font-size:14px and 11 say 16px where they mean small/label and body. The rendered scale is correct — only the authoring is loose. Not a second scale, and not a reason to read a number off the stylesheet instead of off this table.
· 17px tr.lic-row .lp-head — the licence name on a phone card, one step above body-sm so the card has a clear headline. The only 17px in the prototype.
· 14.5px .am-celltop — a half-pixel nudge on the add-ons matrix so a long cell fits its column. Below the floor by half a pixel; kept because rounding it up reflows the table.
· Two mono stacks — .mono uses the raw system stack, while --font-mono (Ubuntu Mono) is used only by .nl-keybox code and this page’s own chrome. The key therefore renders in two different faces depending on where you meet it.

Error state .field.err > .fielderr

Monochrome, so the fault is not carried by hue: the border goes to ink and thickens, and the reason appears under the field in the slot .help would have used — .help is hidden while an error shows, because two lines under one field, one of them now wrong, is worse than either alone. The message says what is wrong, not that something is. “Use MM / YY” can be acted on; “invalid” cannot.

The rule that goes with it: a primary action is never left disabled with nothing said. Either it is enabled and answers on submit — painting every failure at once and moving focus to the first — or it is disabled with the reason visible beside it. The purchase wizard’s billing step and the update-card modal both take the first form, and a .formerr summary sits with the button naming how many fields are waiting. Fields answer on blur, and typing again withdraws the answer.

Snackbar .snack

A transient message at the bottom of the viewport. It reports that something happened, then leaves on its own (4.2s) — with a dismiss for the impatient. It never covers the thing it is reporting about: one line tall, in the margin below the content, and on the phone it sits above both the bottom navigation bar and the prototype’s gear button. role="status", not alert — an alert interrupts, and a confirmation of something you just did has no business taking the cursor.

Confirmations leave; problems stay. The snackbar carries completed actions — Invitations sent to 3 people, Invite link copied. It never carries a field error: Already has access, an invalid address, an empty required field all stay inline beside the input, because the person reads them while fixing the thing they describe, and a message that removes itself on a timer is the worst place for an instruction someone has to act on.

Snackbar or saved note? .snack vs .savednote

They coexist, and they are not two ways of doing one thing. The split is what the message is, not how loud it should be.

 Saved noteSnackbar
Saysa persistent fact about a form — these values are stored, as of thena transient event on a list — this just happened
Livesbeside the button that caused it, in the layoutoutside the layout, at the bottom of the viewport
Leaveswhen the next edit contradicts iton a timer
Used onAccount, Billing, Security — pages with a page-level SaveUsers — pages with a list and no page-level Save

They never appear on the same surface, which is why the pair does not compete: a page either has a Save whose result is a stored state, or it has a list whose result is a changed row. A page-level Save reporting into a snackbar would put a fact on a timer; a list action reporting into an inline note would leave a receipt sitting next to a control the reader has finished with.

Invite block .setcard.invitecard

Not a new container — the existing .setcard, used for a component rather than a settings section. The same card in both states of the Users page, so the two read as one thing that gains a table: in the solo state it holds a heading line, the field and the access sentence; in the table state it drops the heading and sits directly above the toolbar.

Its height does not change. The message slot is always in the layout (visibility, not hidden, and exactly one line tall), confirmations go to the snackbar which is outside the layout, and nothing is revealed inside it on copy. Measured through rest, duplicate, invalid, empty and successful invite, and copy: 135px throughout on the desktop, 284px in the solo state.

Baseline block .nl-pe.baseline

Sits between the billing tabs and the plan cards on both selling surfaces. It states what every plan of the selected product includes, so the cards below it can carry only what differs. Not a card: a rule above it rather than a border around it, so it reads as a preamble to the row below instead of a fourth option in it.

Two things it does that a static block would not. It is contextual — it changes with the product and the billing mode. And where the copy does not exist it says so: .nl-pe.is-gap is a dashed variant carrying a sentence about what is missing, which is the honest alternative to writing product facts nobody approved.

Below 600px the per-item descriptions (.nl-pe-d) are dropped and the names run inline. Measured: the full block was 530px of an 844px viewport and pushed the first plan card to y=1112 — the page opened on a feature list with no price in sight.

New-account empty .emptybox.eb

The same .emptybox the one-line empties use, holding three parts instead of one sentence: what this page is, what will appear here, and at most one action. The parts are optional, so the one-line form still renders exactly as it did.

Only one page carries a primary. A new account has exactly one thing to do, and invoices and activity fill themselves as a side effect of it — so Licenses gets the button, Invoices gets a quiet link back to it, and Activity gets no action at all. Four buttons saying different words for the same next step would be four decisions where there is one.

An empty page shows no chrome that operates on rows — no search, filters, sort headers, pagination, items-per-page or refresh. There is nothing to search or sort, and it all comes back with the first row (body.list-empty).

⚠ Not the same block as .noresults. Solid border here, dashed there, and the difference is not decoration: this one describes the account — nothing exists yet, go and make some — while that one describes the view, is a consequence of what the reader typed, and its exit is to clear the search. Two different facts must not look like one.

No results .noresults

Not the same thing as an empty state, and deliberately not the same block. .emptybox says nothing here yet and waits for you to create something; this says nothing matched and waits for you to undo a filter you set — so it carries the way out. Dashed rather than solid, because it describes a temporary condition of the view rather than a fact about the account.

No matches for “gateway”

Used by all five working searches: Licenses, Invoices, Users, Activity and the licence’s own Activity tab. Inside a table it is wrapped in td.noresults-cell so it does not draw a cell’s borders as well as its own.

Solo state .solo + .inviterow

A third kind of empty, and the only one that is not a box inside a surface: the surface itself is gone. When the Users page has one user — you — the table, its toolbar and its pager are all removed rather than shown holding a single row. There is nothing to search, sort or page through, and a one-row table of yourself is a control panel for a decision nobody is making. What replaces it is the control that changes the state, not an illustration of the state.

You’re the only person with access.

Anyone you invite gets full access to your licenses, invoices and payment method.

The same .inviterow stays on the page in the table state, directly above the toolbar — it is not a card, has no border and no heading, because it is how the list grows rather than a panel you operate. The access sentence is permanent only here, where it is read before the first invite; in the table state it appears under the field as part of the confirmation. Below 600px the row stacks: full-width input, full-width Invite, the link quietly beneath — same position, and never a bottom sheet.
